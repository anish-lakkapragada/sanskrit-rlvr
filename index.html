Sanskrit is a programmable language.
We ran it on a compiler.

Around 400 BCE, Pāṇini compressed the grammar of Sanskrit into ~4,000 ordered, exception-handled rewrite rules — the oldest formal system humanity has. For 2,300 years it could only run on people. We ported a fragment of it to the Lean 4 proof assistant, where a sentence of Sanskrit is grammatical if and only if its check compiles — and then used that compiler to teach a language model to write Sanskrit, with no human labels anywhere.

01The oldest program

Pāṇini's Aṣṭādhyāyī is not a description of Sanskrit. It is a generator of it: start from a stem and a meaning-slot, apply the rules in order, and the correct word falls out. Rules trigger other rules; metarules say which rule wins when two apply. Modern linguists call it the first generative grammar; programmers will recognize something more familiar — a rewrite system with a well-defined execution order. That is code, and code can be ported.

What "formalized in Lean" means

A proof assistant is a program that checks proofs — mathematics with a compiler behind it. We wrote the grammar's rules as executable Lean definitions: the sound inventory, the declension of seven noun classes across 8 cases × 3 numbers, verb conjugation, the sandhi rules for undoing word-boundary fusion, and the agreement laws (subject–verb, adjective–noun). Stacked together they define one decidable proposition, Grammatical s — and "decidable" means the machine can settle it, one way or the other, for any sentence you hand it:

-- "Rāma goes to the village" — the kernel accepts the proof ✓
example : Grammatical "rāmo grāmaṃ gacchati" := by native_decide

-- plural subject, singular verb — this file does not build ✗
example : Grammatical "bālāḥ grāmaṃ gacchati" := by native_decide

-- and the rejection is itself a theorem ✓
example : ¬ Grammatical "bālāḥ grāmaṃ gacchati" := by native_decide

How one judgment runs

The gold paradigm tables are stated as theorems inside the library and re-proved by the kernel at every build — the grammar tests itself. The same definitions compile to a 20 ms command-line judge, which is what makes the next part possible.

Scope, plainly: this is a fragment — seven vowel-stem noun classes, present tense, ~100 lemmas, boundary sandhi undone rather than applied. But it is a real fragment, derivational all the way down, and it grows by adding rules, not data. (The declension tables were cross-checked against vidyut-prakriya, an independent Pāṇinian engine, on 2,496 cells.)

02If it compiles, you can teach with it

Anything a program can verify, a model can be trained on. That recipe — RLVR, reinforcement learning with verifiable rewards — is what powers the current wave of math and code models: math has answer-checkers, code has tests. And now a natural language has a compiler. A compiler is a teacher that never tires, never guesses, and cannot be flattered.

The tasks come from the formalization itself — its lexicon exports 1,989 inflected forms that seed grammar questions ("what is the instrumental singular of rāma?"), translation ("The beautiful girl obtains the garland"), and free composition. The reward is structural, not string-matching: the Lean checker verifies who does what to whom, so a grammatical sentence with the roles reversed scores low. Supervised examples, where used, are also generated by the grammar — zero human labels end to end. Everything ran on an 18 GB MacBook.

The curiosity we tested along the way: which teaches better, supervised examples or reinforcement learning?

Both signals come from the same place — the compiler. The difference is how you use it. Distillation does the lifting: supervised training on answers the grammar generates for itself took the model from 2% to 85% in two epochs. RL alone cannot bootstrap: with almost no correct samples to reinforce, 600 iterations from the untrained model moved nothing (2% → 3%) — and pushed further, the run eventually destabilized. RL after distillation polishes at the margin: from its true starting point (the re-quantized SFT model) GRPO recovered about a point of compile rate (81.5% → 82.4%), less than the quantization step between stages had cost. If you can enumerate the truth, teach by example; RL's room begins where enumeration ends.

05What this shows — and doesn't

  • Shown (i): a natural language's grammar — a genuine fragment of Pāṇinian Sanskrit — can live in a general-purpose proof assistant, with grammaticality as a machine-checkable proposition and the paradigm tables as theorems. Type-theoretic linguistics has a real lineage (Grammatical Framework; natural-language semantics in Coq and Agda); to our knowledge this is the first machine-checked Pāṇinian grammar fragment in a prover.
  • Shown (ii): the standard RLVR pipeline runs end-to-end against it — to our knowledge the first RL training whose verifiable reward is a prover-checked judgment of natural-language grammaticality rather than math or code.
  • Not shown: all of Sanskrit (one tense, no consonant stems, no compounds); semantic understanding (the checker verifies structure, not meaning); any claim that RL beats supervised learning here — it didn't, and we report that straight.

Pāṇini's grammar was always a program.
It just waited 2,300 years for a runtime.

06Reproduce

One Lean library (lean/ — lake build replays every theorem), one Python file (rlvr.py — tasks, reward, eval, snapshots), one reward shim (rewards.py). Data and gold answers are generated by the formalization itself. Evals in results/. Model: Qwen3-4B-Instruct-2507 (4-bit, MLX) with LoRA; trainer: mlx-lm-lora; metrics: Lean compile rate, exact match, chrF++ (sacrebleu). Hardware: one 18 GB M3 Pro MacBook.
