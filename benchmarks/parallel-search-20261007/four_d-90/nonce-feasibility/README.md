Vidyut can generate forms from a hypothetical root citation and class. This is technically feasible as a **formal nonce-inflection diagnostic**, but the generated forms do not thereby become licensed classical Sanskrit. Using these roots in the benchmark would change its dictionary-root domain and requires an explicit user scope decision. This audit authorizes no such change.

The installed Vidyut 0.4.0 constructor accepts `Dhatu.mula(aupadeshika, gana, ...)`. It takes no dictionary code or meaning and does not require a dictionary lookup. The inspected upstream Rust constructor stores the supplied citation/class with empty prefixes and derivational operations. Its builder checks the required fields and SLP1 representation. The documentation expects an appropriate root citation, including relevant accents; it does not promise to establish lexical validity. Upstream `main` is supporting source evidence, not a claim of byte identity with the installed binary, whose hash is recorded locally. [Official API](https://vidyut.readthedocs.io/en/latest/api.html#vidyut.prakriya.Dhatu.mula), [official constructor source](https://github.com/ambuda-org/vidyut/blob/main/vidyut-prakriya/src/args/dhatu.rs).

Exactly six inputs were run offline. All use **Lat, Kartari, Prathama, Eka** (present, active, third-person singular). No pada, prefix, Sanadi operation, or subgroup was supplied. This is **not** proof of unattestation throughout Sanskrit literature. A surface output may separately have another analysis. The present-only examples establish API behavior, not support for every other tense or voice. The `1.3.1` step in all six engine traces reflects the engine's assumption that its argument is a root; it is not an independent source check.

The grammatical distinction matters. Kāśikā 1.3.1 relates root designation to the action-denoting bhūādi words, and Nyāsa explicitly refers to the ten transmitted classes. The same page discusses broader traditional categories, so this audit does not claim that one modern TSV exhausts every possible Sanskrit root. It does establish that supplying an arbitrary spelling and class to software is not itself a traditional licensing argument. [Primary commentaries on 1.3.1](https://sanskritdocuments.org/learning_tools/ashtadhyayi/vyakhya/1/1.3.1.htm).

Rule 3.1.32 supplies a distinct route for specified Sanadi-derived formations to receive root designation. Vidyut exposes a separate `Dhatu.nama` constructor for nominally derived roots, with rule-dependent behavior. Neither is a justification for silently treating arbitrary invented strings as dictionary mūla roots under the current ordinary-conjugation contract. [Primary commentaries on 3.1.32](https://sanskritdocuments.org/learning_tools/ashtadhyayi/vyakhya/3/3.1.32.htm), [official API](https://vidyut.readthedocs.io/en/latest/api.html#vidyut.prakriya.Dhatu.nama).

A separately declared formal task could retain the same four inflection coordinates and stipulate a hypothetical citation/class. It would need explicit global conventions for lexical properties not inferred from spelling: accent/it markers, subgroup defaults, semantic restrictions and optional forms. The examples show that even adding `~` materially changes the result. A missing meaning is harmless for this narrow active-present probe but cannot license arbitrary passive or semantically conditioned uses. Avoid inventing a historical meaning or dictionary identifier to disguise those assumptions.

Recommendation: keep nonce roots out of the current classical benchmark and RL manifest. If the user later wants a synthetic generalization task, label and validate it separately. New strings increase numerical family supply but do not establish new grammatical mechanisms, independent statistical units, difficulty, or classical correctness. Existing policy holds often refer to exact dictionary entries, so they cannot be assumed sufficient for a nonce domain. The existing benchmark adapter/validator and family split were neither reused as certification nor changed.
