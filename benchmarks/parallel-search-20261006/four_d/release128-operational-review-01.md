**Independent operational review — 7 October 2026.** A fixed 4,800-question evaluation can be staged safely at an Astra 128,000-token cap, but its **completion cannot be guaranteed within the remaining budget**. Smaller transport stages solve reservation liquidity, not total funding. The current runner needs explicit protocol binding, a documented planning-reserve revision and a smaller core partition before this is executable. Existing code dependencies, frozen artifacts, authorization and paid calls were unchanged; a separately authorized, isolated partition helper is now available for later integration.

This review read code and whitelisted ledger accounting fields only. It did not read model answers or pilot07 scores. [Arithmetic and proposed stage records](release128-operational-review-01.json) were generated by [the isolated offline checker](../../../misc/vp_4d_release128_review.py). Its seven assertions passed. Figures below use the parent's settled-spend baseline: Anthropic $188.615334 and OpenAI $727.478150. During review, accounting advanced to Anthropic $217.754816 settled plus $200.208 reserved for the remaining 1,200-question confirmation; this is recorded separately, without changing the baseline scenarios.

OpenAI has $1,272.521850 remaining: only 396 questions are affordable at their individual maxima, ignoring all other future allocations. The full 4,800 therefore requires savings released from actual settled usage. Anthropic's baseline minus the **full planned 2,400-question confirmation maximum** leaves $410.968666, which likewise cannot guarantee the entire final evaluation even at 16,384. Both provider lifetime caps remain hard limits, and unused Anthropic money cannot fund OpenAI.

The settled 60-question Astra diagnostic cost $14.450675, averaging $0.240844583 per question. Extrapolating that mean gives a **conditional scenario**, not a representative or upper-bound forecast: $1,156.054 for the final evaluation, $1,883.532150 lifetime, and $116.467850 left afterward. The absolute mean-cost affordability ceiling is $0.265108719 before any other OpenAI spend. Earlier 16,384-token cost estimates must not be treated as a guarantee for the new cap. Opus 16,384 development usage can inform a separate forecast; moving Opus to 128,000 would require an explicit protocol decision and appropriate cost caveat.

| 1,001–3,000 | 100 | 20 | `hard_extension` |

This is 114 stages per provider, 228 provider-stage jobs, using identical task files for both references. It preserves every task and the first 1,000 core questions exactly. The existing `audit_partition` already accepts multiple core stages; `freeze` currently hard-codes one core stage and must accept an explicit stage-size schedule instead. Freeze all stage sizes before any final answers. Never resize, omit or reorder them in response to outcomes.

With no outstanding jobs or other planning reserves, the last Astra batch needs $16.037500 available immediately before submission. Under the constant diagnostic-mean scenario, headroom **after reserving that maximum** is $101.634573; the minimum such headroom anywhere in the proposed schedule is $90.470381. Uniform 100-question batches instead block at stage 41, after 4,000 questions, despite the total expected cost fitting. The taper also passes constant-cost scenarios of $0.25 and $0.26 per question, but fails at $0.263 even though total realized cost would fit: the strongest prefix constraint is approximately $0.260619530. Uneven actual costs or other spending can block it earlier. In the true worst case, there is no funded last-stage headroom because the evaluation stops much earlier.

Necessary changes to the execution path are concrete:

1. **Version the final protocol without reinterpreting existing jobs.** Today `PHASES[phase][1]` is shared across providers and is used by request rendering, validation, reservation and collection. `load()` also compares the complete phase policy against the ledger. Do not simply change it to 128,000: that either fails the authorization check or makes historical prepared requests fail validation. Add an authorized, immutable protocol ID bound to each final job and the release manifest, with explicit provider/phase/effort/cap. Resolve the same record in `request`, `validate_requests`/`verify_job`, `budget_gate` and `finish_job`; preserve legacy jobs' original protocol. If only Astra changes, Opus must retain its explicit original cap. Existing question allowances remain 1,000 core and at most 5,000 extension.

2. **Reassign internal planning reserves explicitly.** `protected_remaining` currently protects both 1,000-question cores and the unused cap-check allowance. A 128,000-token protected Astra core alone costs $3,207.50; splitting it cannot unlock even the first stage because each submission replaces only its portion of that protection. A documented coordinator reserve revision must release the unused 4D core protection and the unfunded blanket future-core protection in favor of rolling, actual stage reservations. The 60 completed diagnostic requests leave 40 protected cap-check slots, costing $128.30; retaining those is inconsistent with the diagnostic-mean 4,800 scenario's $116.47 residual. Setting those *minimum planning allocations* to zero (or the cap-check minimum to the 60 already consumed) does not increase phase allowances or provider caps. Any other future work needs an explicit retained allocation and a revised funding calculation. There is no full-run financial guarantee to preserve here.

3. **Bind execution to this release and protocol.** Extend the manifest's current phase-only protocol dictionary and job identity checks. Under the paid-submission lock, require the exact authorized release hash, stage index/digest, provider and protocol ID; reject changed stage files, dependencies, membership or request caps. Check the core barrier against this release's exact core stages, rather than the runner's global phase totals. Specify whether both providers' core receipts must settle before any extension; the current code only enforces each provider separately. An exact both-provider barrier is a clear interpretation of the manifest's “settle all core” wording. Final analysis must also match the bound protocol when identifying stage jobs; matching only provider/phase/task digest is insufficient after adding protocol versions.

4. **Treat affordability races as waits only before submission intent.** `execute` preflights a budget, counts inputs, then calls `submit`; another ledger writer can consume headroom in between. The locked budget gate remains the authority. Return a structured “not submitted, budget wait” result before setting `attempted_at`, or classify it using the freshly loaded ledger. Do not blindly retry a failed `submit`: once an intent exists, keep its full reservation and reconcile its receipt. If there are unsettled reservations, wait for collection; if everything is settled and the next fixed stage still cannot be reserved, report `unfunded_incomplete`. No score, SE or response correctness enters that decision.

The present durable-intent-before-POST, locked lifetime-cap check, full unknown reservation, duplicate-final-question rejection and terminal-usage settlement rules should remain intact. Run a separate collector so receipts actually release savings. Allow multiple outstanding fixed stages only while their **sum of maxima** fits. The runner's 12-hour default/24-hour invocation limit may be shorter than multiple batch waves; expiry should record an incomplete run and permit resuming the same release and job prefix, without replaying attempted stages. A deadline is not permission to publish a partial benchmark.

Conceptual submission logic, after freezing and separate coordinator authorization:

```text
for the next unattempted fixed stage for each provider:
    verify release, stage, protocol, exact input counts and core receipts
    under shared ledger lock:
        reload all lifetime spend and outstanding/unknown reservations
        reject any existing paid intent or duplicate task attempt
        reserve = n * (1500 * input_rate + frozen_cap * output_rate)
        if committed + reserve + retained_other_allocations > provider_cap:
            return WAIT_FOR_RECEIPTS or UNFUNDED_INCOMPLETE
        persist paid intent and full reservation
        perform the single submission; persist receipt or retain unknown status
continue until all fixed 4,800 tasks for both providers settle
```

The new [transport helper](../../../misc/vp_cartesian_transport.py) exposes `partition_tasks(tasks, *, core_phase, extension_phase, schedule)` and performs no I/O or runner imports. It validates increasing endpoints, the exact final count and chunk sizes 1–1,000; it cuts automatically at the core boundary and preserves task objects/order. [Nine focused tests](../../../misc/test_vp_cartesian_transport.py), including 100 seeded schedule cases, passed. Applying it to candidate04 also passed the existing `audit_partition` check: 4,800 total, 1,000 core, 3,800 extension, 114 stages. [Verification receipt](transport-partition-review-01.json) confirms the existing release/runner dependencies still match their pre-review hashes. The helper is not integrated or authorized to submit anything.

Before installing the remaining changes, add focused offline checks for legacy protocol preservation, changed-cap rejection, split-core settlement barriers, concurrent reservation races, unknown submission handling and restart behavior. The arithmetic checker already demonstrates a next-stage funding failure despite affordable expected total cost. Make code/protocol changes and regenerate dependency hashes only after the running development work is safely reconciled. This proposal does not change the accuracy/precision gates or approve final evaluation spending.
