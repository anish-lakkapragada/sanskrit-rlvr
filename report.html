Sanskrit is a programmable language.
We ran it on a compiler.

Around 400 BCE, Pāṇini compressed the grammar of Sanskrit into ~4,000 ordered, exception-handled rewrite rules — the oldest formal system humanity has. For 2,300 years it ran only on people. We ported a fragment to the Lean 4 proof assistant, where a sentence of Sanskrit is grammatical if and only if its check compiles — then used that compiler as the training signal for an open language model, comparing supervised fine-tuning with the canonical SFT→GRPO reinforcement pipeline. No human labels anywhere. One 18 GB MacBook.

01The oldest program

Pāṇini's Aṣṭādhyāyī is not a description of Sanskrit — it is a generator of it. Start from a stem and a meaning-slot, apply the rules in their prescribed order, and the correct word falls out. Rules trigger other rules; metarules resolve conflicts. Linguists call it the first generative grammar. A programmer will recognize something more specific: a rewrite system with a defined execution order. That is code — and code can be ported.

Grammar as derivation, not lookup

No table in the formalization contains "rāmeṇa". A rule fires — because of the r earlier in the word — and the machine derives the retroflex ṇ, the same way a Pāṇinian grammarian would:

rāma + instrumental sgrāmeṇa रामेणn → ṇ after r within the word (ṇatva)
deva + locative pldeveṣu देवेषुs → ṣ after e (the ruki class)
dṛś + present 3rd plpaśyanti पश्यन्ति'see' swaps to a suppletive stem

What "formalized in Lean" means

A proof assistant is a program that checks proofs — mathematics with a compiler behind it. We wrote the grammar's rules as executable Lean definitions: the sound inventory, declension of seven noun classes across 8 cases × 3 numbers, verb conjugation, sandhi-undoing at word boundaries, and the agreement laws. Together they define one decidable proposition, Grammatical s — "decidable" meaning the machine settles it, one way or the other, for any sentence, of any length (clauses chain with ca, Sanskrit's "and"):

-- "Rāma goes to the village" — the kernel accepts the proof ✓
example : Grammatical "rāmo grāmaṃ gacchati" := by native_decide

-- a three-clause sentence checks the same way ✓
example : Grammatical
  "rāmo grāmaṃ gacchati kanyā ca mālāṃ labhate munayaś ca satyaṃ vadanti" :=
  by native_decide

-- plural subject, singular verb — this file DOES NOT BUILD ✗
example : Grammatical "bālāḥ grāmaṃ gacchati" := by native_decide

-- and the rejection is itself a theorem ✓
example : ¬ Grammatical "bālāḥ grāmaṃ gacchati" := by native_decide

The paradigm tables are theorems, re-proved by the kernel at every build — the grammar tests itself. The same definitions compile to a 20 ms command-line judge with --json diagnostics, which is what makes the next part affordable: it scored roughly half a million model outputs overnight. Scope, plainly: a fragment — 7 vowel-stem classes, present tense, ~125 lemmas, sandhi undone rather than applied. Real, derivational all the way down, and it grows by adding rules, not data.

02If it compiles, you can train on it

Anything a program can verify, a model can be trained against — that's RLVR, the recipe behind the current generation of math and code models. Math has answer checkers; code has tests. Now a natural language has a compiler — a teacher that never tires, never guesses, and cannot be flattered.

Tasks come from the formalization itself: its lexicon exports 2,286 inflected forms that seed grammar questions, hint-free translation, and four-word composition. The reward is structural — the checker verifies who does what to whom, so a grammatical sentence with reversed roles scores low. Supervised data, where used, is also grammar-generated: zero human labels end to end. Each experiment is one YAML config (model, data, hyperparameters, eval cadence); every run leaves a self-describing directory — frozen config, training log, four checkpoints, metrics, and the model's actual generations at every quarter of training.

03What happened

Two arms, evaluated at every quarter of training on held-out prompts (greedy decoding, judged by Lean): pure SFT on grammar-generated answers, then the canonical SFT → GRPO pipeline on top of it.

Every point is a real checkpoint evaluation (a fixed 60-prompt slice, generations preserved under runs/…/snapshots/; the table below uses the full benchmarks, hence small differences). The dashed red step between phases is the price of the pipeline itself on an 18 GB machine: chaining GRPO onto SFT requires fusing the SFT adapter and re-quantizing to 4-bit — 5.1 points gone before RL begins. GRPO climbs back steadily from there.

So which trains better — supervised examples or reinforcement?

Both signals come from the same compiler; the difference is how you spend it, and the answer splits cleanly in two. In distribution, imitation does the lifting: two epochs of SFT on grammar-generated answers took compile-rate from 2.8% to 77.8%, and GRPO on top only ties it (78.7%) — RL climbed steadily from its re-quantized starting point but roughly repaid the pipeline toll, no more. Out of distribution, reinforcement wins: on vocabulary neither arm ever trained on, the GRPO model answers 53.3% of inflection questions against SFT's 43.3% and edges it on compiling sentences. Imitation memorizes what the teacher shows; RL — rewarded only for being right, never shown how — appears to lean harder on the rule. (In an earlier iteration we also ran GRPO from scratch as a control: 600 numerically-perfect iterations, zero movement. With almost no correct samples to reinforce, there is nothing to climb — the SFT stage is not optional.)

Generalization — including beyond what the grammar models

Training data is restricted to the fragment's core vocabulary. The benchmarks are not: a held-out tier of lemmas exists in the Lean model but never in training data (unseen words, still kernel-judged), and a beyond-fragment set of classical maxims and textbook lines uses tenses and stems the formalization doesn't model at all (judged by chrF++ against references — Lean cannot judge what it doesn't model).

The generalization is real and kernel-verified: on lemmas that exist in the Lean model but never appeared in any training file, the trained model goes from zero compiling sentences to ~31%, and from 10% to 53% on inflection questions — it learned declension patterns, not answers. Beyond the fragment (tenses and stems the grammar doesn't model), chrF++ rises 3.7 → 13.5: the model transfers its in-fragment habits (word choice, agreement) but cannot conjure the perfect tense from nowhere — the honest boundary of what a fragment can teach.

05What this shows — and doesn't

  • Shown (i): a genuine fragment of Pāṇinian Sanskrit lives in a general-purpose prover, with grammaticality as a kernel-checkable proposition and the paradigm tables as theorems. Type-theoretic linguistics has a real lineage (Grammatical Framework; natural-language semantics in Coq and Agda); to our knowledge this is the first machine-checked Pāṇinian grammar fragment, and the first RLVR setup whose reward is a prover-checked judgment of natural-language grammaticality rather than math or code.
  • Shown (ii): the standard post-training pipeline runs end-to-end against it, instrumented enough to say precisely what each stage contributed — including the honest negative (RL does not beat its own pipeline toll here) and the honest positive (the model generalizes the grammar to words it never saw in training).
  • Not shown: all of Sanskrit (one tense, no consonant stems, no compounds); semantic understanding (structure is checked, meaning is not); any claim that GRPO beats SFT on this fragment — it didn't, and the numbers say so.

Pāṇini's grammar was always a program.
It just waited 2,300 years for a runtime.

06Reproduce

One Lean library (lean/ — lake build replays every theorem), one experiment framework (finetune/ — YAML configs in, self-describing run directories out), one data directory with a README that maps every file to its experiment. bash finetune/run.sh finetune/configs/sft-baseline.yaml reproduces Phase 1; sft-then-grpo.yaml chains Phase 2. Model: Qwen3-4B-Instruct-2507 (4-bit, LoRA rank 8 on 16 layers) via mlx-lm-lora on Apple MLX; metrics: Lean compile-rate + chrF++ (sacrebleu, standard settings). Hardware: one M3 Pro MacBook, 18 GB.
